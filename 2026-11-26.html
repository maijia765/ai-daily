GPT-6 设计的蛋白质在实验室中成功结合

OpenAI 11 月 24 日发文称，GPT-6 家族模型仅凭推理和通用代码工具就能设计新的蛋白质三维结构与氨基酸序列，设计步骤本身不调用专用生物学模型。OpenAI 与研究伙伴 Onava 把 GPT-6.2 的设计做成实物蛋白做实验室测试：322 个针对 5 个靶点（PD-L1、IL-7Rα、TrkA、VEGF-A、IL-17A）的迷你结合蛋白中，35 个（10.9%）显示出结合证据，每个靶点至少有一个阳性。重新设计已知迷你结合蛋白的序列时，MDM2 靶点 75/88（85%）、VEGF-A 26/42（62%）、PD-1 8/59（14%）保留了结合；抗体结合环重设计 128/182（70%）仍能结合。在 14 项蛋白质任务的计算评估中，OpenAI 内部较新的模型在多数任务上达到或超过专用模型，但完整蛋白质结构预测仍是明显短板；实验中氨基酸序列的生成与候选筛选仍由专用模型完成。相关预印本题为《GPT-6 as a Universal Foundation Model for Protein Biology》。

为什么重要： 通用大模型第一次在湿实验室里拿出蛋白质结合的证据——设计步骤不再依赖专用生物模型。但 10.9% 的命中率、仍需专用模型提供序列与筛选候选，说明这还不是端到端的替代，而是"通用模型写草图、专用模型筛候选"的新分工；真正值得看的是这个分工能不能把蛋白质设计从专家工具变成自然语言任务。

OpenAI 预印本称矩阵乘法指数恰为 9/4，Lean 证明只覆盖部分结论

OpenAI 11 月 24 日在 GitHub 的 openai/math 仓库发布预印本《The matrix multiplication exponent is nine fourths》，称矩阵乘法指数 ω 恰为 9/4（即 2.25），覆盖所有数域。上界 ω ≤ 9/4 在 10 月 2 日的预印本中已有提出，这次补上的是匹配的下界：n ≥ 2 时，形式算术电路做 n×n 矩阵乘法至少需要 ⌈n^(9/4)/2⌉ 个非标量乘除门。同一批预印本还包括 11 月 23 日的 VP ≠ VNP 证明，Anthropic 同日也发布了自己的 VP ≠ VNP 解答；OpenAI 称 11 月 24 日的预印本取代了 11 月 23 日的版本。需要同时写明的限定是：随附的 Lean 形式化证明只覆盖无除法电路，比论文主结论的范围窄；预印本未经同行评审，外部尚未核查。

为什么重要： 如果成立，ω = 2 的猜想就此终结——自 Strassen 1969 年的算法以来悬而未决的问题有了答案。但要注意这是算术电路门数的理论结论，不等于真实硬件上的矩阵乘法会变快；Lean 只验证了部分结论，结论的份量与待核查的程度要同时记在账上。

开发生态

Claude 的 artifacts 可一键安装为桌面应用，最高可申请完整电脑访问权限

Anthropic 11 月 24 日推出 "Install as app" 测试版，Claude 的 artifacts 可一键安装为 Mac 与 Windows 桌面应用：独立图标与窗口、可分享给他人，无需打包、签名或单独的 API key，调用 Claude 与连接器，artifact 修改后应用自动更新。权限分三档：默认仅限浏览器能力；应用权限可申请通知、全局快捷键、置顶窗口与菜单栏图标；完整电脑访问可运行程序、读写删除文件且无需每次确认——仅限自己或组织内制作的应用，Anthropic 事先不审核应用，每次更新后需重新授权。需要 Claude for Mac 或 Windows 6.28899.0 或更高版本，所有套餐均在测试版推送中；Team 默认开启、完整访问默认关闭，Enterprise 需管理员手动开启，HIPAA 配置的组织不可用；应用需联网并登录 Claude 才能打开，Docs、Slides、Sheets 等模板类 artifact 不可安装。

Anthropic 用 Claude 把核心 API 从 Python 迁到 Rust，生产系统本身当验证器

Anthropic 11 月 25 日发工程博客，介绍把 Messages API 从 Python 全面迁移到 Rust 的过程。Messages API 是客户与 Claude Code、Cowork 等自家应用访问 Claude 的主要通道，流量自 2024 年初至 2026 年秋增长约 1800 倍。Claude 约一周写出核心请求路径的初版；到 2026 年 5 月，Claude 已写了 Anthropic 合并代码的 80% 以上。真正的难点是验证：约 700 个集成测试与 Python 实现绑定，移植后审计发现 100 多处被弱化的断言；4 月 Rust 版测试通过率约 98%，但在真实生产流量上仅约四分之一的输入行为一致。团队的解法是把生产中的 Python API 当作"标准答案"：同一份请求只调用一次模型、把输出同时回放给两个版本比对，只记录差异的形态而不读用户内容；Claude 智能体自动分组、复现并修复差异，匹配率从 4 月底的 24% 升至 8 月的 99.6%，9 月完成流量切换，全程不停机、不冻结功能开发。成效按 Anthropic 自述：每请求 CPU 减少约 70%、内存减少 80% 以上、首 token 中位延迟降低约 20%。

为什么重要： 这不是"AI 写了多少代码"的数字游戏，而是"AI 怎么证明自己写的代码和线上系统行为一致"的方法论——用生产系统本身当验证器、把差异而不是测试用例当作修复单位。不过数字是厂商自述，CPU 图表只覆盖一个区域，仍待独立验证。

OpenAI 与思科开源 Shirudo：给 Linux 漏洞先加临时"护盾"，不用停机等补丁

OpenAI 与思科 11 月 24 日推出开源运行时 Shirudo（日语"盾"），用 eBPF 在 Linux 内核里给漏洞临时加"护盾"：先验证护盾能否挡住攻击行为、同时放行合法请求，操作员批准后部署，无需重启服务；等正式补丁装好，护盾退役。智能体可编程调用整套流程：发现漏洞、生成针对性护盾、在沙箱里复现验证；护盾经密码学签名、经 Linux eBPF 验证器校验，TPM 提供护盾加载与移除的可验证记录。两人已演示用它防护运行中的 Elasticsearch 抵御 Java4Shell 攻击。Shirudo 以 BSD 2-Clause 开源，BPF 程序双许可 BSD/GPL，技术源于思科 Isovalent 的 Tetragon。

为什么重要： AI 发现漏洞的速度已经超过人类打补丁的速度，Shirudo 把"先挡住、再慢慢修"做成机器可执行的标准动作——防御第一次有了和攻击一样的自动化节奏。但护盾本身由智能体生成，护盾写错、误拦合法请求的责任链还在人手里，批准环节不能省。
